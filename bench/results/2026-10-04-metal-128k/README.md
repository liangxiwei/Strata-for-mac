# Mac 上的 128K 上下文，2026-10-04

> 仓库里保留本目录的 README、汇总（`iq2_xs.json`、`q2_0.json`）和驱动脚本；原始运行输出（`run/`）只留在测量的机器上，不进 git。

Apple M2 Max（38 核 GPU、96 GB），macOS 26.5，引擎二进制与 `../2026-10-04-metal-models/` 相同。

## 测法

用 setup 写出的配置，只把 `--max-context` 改为 131072，并去掉图片参数，只测文字路径。其余参数和每天用的一样：FP16
KV，1,024-token 分块，专家全部常驻。

提示按 `../2026-10-03-metal-100k/` 的方法生成：

- 正文是仓库自己的文档和 `src/core/*.cpp`。
- 正中间埋一条校验记录：项目代号 银杏，验收日期 10月18日，校验码 AX-7319。
- 结尾要求用一句话答出这三项。
- 套上对话模板后正好 128,000 个 token。

每个模型都从新进程开始，不复用前缀，temperature 0，关闭思考。答完后在同一会话里追问一次"校验码是多少"。

## 结果

| | IQ2_XS | Q2_0 |
| --- | ---: | ---: |
| 读入 128,000 token | 907.0 s，**141.1 token/s** | 897.6 s，**142.6 token/s** |
| 首个 token | 907.1 s | 897.7 s |
| 读完后写回答 | 24.5 token/s（26 token） | 23.1 token/s（26 token） |
| 三个字段 | **3/3**：项目代号为银杏，验收日期为10月18日，校验码为AX-7319。 | **3/3**：项目代号为银杏，验收日期为10月18日，校验码为AX-7319。 |
| 追问：复用 / 新读 | 128,025 / 24 token，0.88 s | 128,025 / 24 token，0.84 s |
| 追问首个 token | **0.95 s**，回答 AX-7319 | **0.91 s**，回答 AX-7319 |
| 全部载入后剩余的 GPU 内存 | 36,776 MiB（32K 时 39,453） | 38,334 MiB（32K 时 41,011） |
| 引擎 physical footprint 峰值 | 未保存，见下 | **41.9G**（`vmmap`，每 15 s 采样） |

读入速度随长度下降：30,000 token 时约 196-202 token/s，128,000 token 时 141 token/s。写回答的速度不受影响，每个
window 约 40.8 ms。容量从 32K 增加到 128K，按引擎报告的剩余 GPU 内存算，引擎多用了约 2.6 GiB（两个模型都是：39,453 → 36,776 和 41,011 → 38,334 MiB）。Q2_0 在 128K 时引擎 physical footprint 峰值为 41.9G。

IQ2_XS 那次运行写汇总时因路径问题失败，脚本已修复。`iq2_xs.json` 里的两行是运行时打印出来的结果，启动时间和
footprint 采样没有保存下来。表里的数字和引擎日志 `strata serve: prompt ...` 一致。

`../2026-10-03-metal-100k/` 那次 100K 运行，回答反复输出 "RAM"，没有找到埋入的字段。那时的引擎有 Q3_K 解量化
错误（PROGRESS 第 19 轮修复）。修复后的引擎在 128K 上找回了全部三个字段。不过这只是每个模型一个样本，不能证明长
文本的普遍质量。

## 复现

```sh
.venv/bin/python bench/results/2026-10-04-metal-128k/long_context.py --config strata-iq2_xs.json
.venv/bin/python bench/results/2026-10-04-metal-128k/long_context.py --config strata-q2_0.json
```

一次只跑一个引擎。每次约 16 分钟。
